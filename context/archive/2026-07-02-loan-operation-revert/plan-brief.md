# Loan Operation Revert - Plan Brief

> Full plan: `context/changes/loan-operation-revert/plan.md`

## What & Why

Build an MVP revert capability for two loan operations: loan prepayments and WIBOR/rate changes. The goal is to let a user correct an accidental loan operation from the audit history while restoring the full loan state, not just one edited row.

## Starting Point

Loan schedule changes already use preview plus `ExpectedScheduleVersion` in `LoanService`, which gives us a useful conflict model. Audit logs are currently per entity change, mostly `LoanInstallment` updates, and do not represent one business operation such as "prepayment" or "WIBOR change" as a revertable unit.

## Desired End State

Audit entries for supported loan operations expose a clear Revert action. Reverting a prepayment removes the prepayment record, restores the recalculated schedule, and removes or restores the generated prepayment expense. Reverting a WIBOR/rate change removes the specific rate entry and recalculates the schedule from the affected date. If later loan changes happened, revert is blocked with a clear conflict message.

## Key Decisions Made

| Decision | Choice | Why |
| --- | --- | --- |
| Scope | Prepayment and WIBOR/rate changes only | Keeps the first version focused and avoids building a broad audit revert framework prematurely. |
| Entry point | Audit UI | Matches the user's requested workflow and keeps revert out of routine loan servicing screens. |
| Prepayment effects | Revert prepayment, schedule, and generated expense | A partial revert would leave stale month-plan data and confuse cash-flow totals. |
| WIBOR effects | Remove one `LoanRateEntry` and recalculate schedule | This matches the existing loan model better than replaying raw installment snapshots. |
| Later changes | Block revert | Safer MVP: no attempt to merge or reorder later financial operations. |
| Revert audit | Create explicit `Revert` audit trail | Keeps financial history explainable after corrective action. |
| Authorization | Budget users, not admin-only | Matches the user's choice; backend must still enforce budget ownership. |

## Scope

**In scope:**
- Represent supported loan operations as revertable audit operations.
- Revert prepayment operations, including schedule and generated prepayment expense.
- Revert WIBOR/rate-entry operations, including schedule recalculation.
- Show Revert in audit rows only when the operation is supported and currently revertable.
- Block stale reverts when the loan has changed after the target operation.
- Add service and UI tests for success, stale conflict, authorization, and audit trace.

**Out of scope:**
- Revert installment amount changes from bank.
- Revert arbitrary audit log rows for non-loan entities.
- Merge/replay later loan operations after the reverted operation.
- A dedicated revert screen on the loan workspace.

## Architecture / Approach

Introduce a loan-operation audit layer that groups the entity-level changes generated by `LoanService` into a stable business operation record. Revert commands target that operation record, validate the current schedule version against the operation's post-change version, then use the same schedule projection/persistence path that current loan changes already use.

## Phases at a Glance

| Phase | What it delivers | Key risk |
| --- | --- | --- |
| 1. Operation audit model | Schema and contracts for revertable loan operations | Choosing too little metadata to safely detect stale reverts. |
| 2. Backend revert behavior | Service methods that revert prepayment and WIBOR operations atomically | Accidentally leaving generated expenses or open month sync out of date. |
| 3. Audit UI and tests | Revert button, confirmation, result messages, and coverage | Showing the action for rows that are not safe to revert. |

**Prerequisites:** Existing loan schedule preview/version behavior remains intact.
**Estimated effort:** 3 focused implementation sessions across 3 phases.

## Open Risks & Assumptions

- Assumption: for MVP, blocking revert after any later loan schedule operation is acceptable.
- Assumption: generated prepayment expenses can be identified reliably from `LoanPrepayment` plus current prepayment expense naming/tag logic.
- Risk: existing audit logs before this change will not have operation metadata and should not be revertable.
- Risk: budget-user authorization requires careful checks because the audit page is currently admin-focused.

## Success Criteria Summary

- A supported loan prepayment or WIBOR audit entry can be reverted once, from the audit UI.
- Revert restores schedule/month-plan effects and creates a visible audit trail.
- Revert is blocked when the loan changed after the original operation or when the user lacks budget access.
